# 継続決済の自動紐付け 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 承認済み契約と同内容の継続決済について、毎月の確認を省く。

**Architecture:** 現在停止している新規契約の自動作成は復活させず、既存Workerで承認済み根拠との厳密な照合と根拠追加だけを行う。候補の抽出・除外規則を共有し、通知生成前にも同じ紐付けを適用する。

**Tech Stack:** Go、PostgreSQL、既存Worker。新しい依存・環境変数・DB migrationは追加しない。

**Spec:** [設計](../specs/2026-11-16-recurring-source-design.md)

## 制約・レビュー観点

- 契約・原価・AI応答の内容を変更しない。監査と根拠追加を原子的にする。
- 所有者・接続の分離、曖昧一致、契約変更、除外・予約・古い結果を検証する。
- 自動追加した根拠だけを承認の代わりに使わない。
- 冪等性・同時実行・監査失敗時のロールバックと通知の抑止を検証する。

巡回は30秒間隔とし、全保存済み結果の照合を毎秒繰り返さない。通知生成時は対象メールだけを先に照合するため、巡回待ちで確認通知を作らない。

## レビューで確認した判断

- 本人が承認した署名から対象契約が一意と判定できた後、その契約の現状と予約を検証する。適格性で先に絞り込むと、複数契約の一方に届いた請求を別の契約へ寄せるため。
- 未完了の変更予約がある契約は対象外とする。根拠追加だけでも契約の版が変わり、予約の基準版を無効にするため。
- 承認済み根拠がない所有者は通知前の自動照合を省き、既存の候補評価の共有を維持する。
- 旧形式の自動更新情報への互換処理では、別の料金・イベント種別を含む対象契約の全承認済み根拠から、自動更新停止の指定を確認する。
