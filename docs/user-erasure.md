# Cycrioの退会と利用データ削除

本人が設定の「アカウント」で退会を確認すると、新しい利用を停止し、Workerが利用データとCycrioの認証に使うClerkユーザーを削除します。署名を検証したClerkのユーザー削除イベントも同じ削除処理へ接続します。削除要求は取り消せません。Cycrioの退会は、Google・Microsoftのアカウント削除や、利用先のサブスクリプションの解約を行いません。

## 削除する情報

本人の契約・請求履歴・抽出結果・元メールの識別情報・メール接続・個人用の全バージョンの資格情報・OAuth途中状態・同期カーソル・通知と通知設定・予算設定を削除します。監査の写しに含まれる契約名や抽出内容も削除対象です。共有のAIモデル・価格・管理設定・サービス用APIキー・他ユーザーのデータは削除しません。

本人の認証情報との対応を削除し、元の内部ユーザーIDも残しません。共有の管理操作履歴に必要な作成者・操作主体は、認証やログインに使えない共通の匿名主体へ置き換えます。

## 保持する情報

費用は、本人・メール接続・メール・契約・呼び出し元の識別子を含まない専用台帳へ移します。開始日時は日本時間の月単位に丸め、プロバイダー・モデル・処理段階・使用目的・原価区分・通貨・金額・結果を保持します。原価不明を0円にはせず、遅れて確定した原価や訂正も反映します。通常の利用者別・メール別・呼び出し履歴からは切り離し、管理者の月次合計には含めます。

本人の監査は、月・機能・操作種別・件数だけを残します。契約名、金額以外の任意入力、JSONの写し、元ユーザーIDなどは監査の集計へ持ち込みません。

遅着した原価を二重計上せず照合するため、元のAI呼び出しIDの一方向ハッシュを保持します。削除済みの認証主体から遅着Webhookで個人情報を復活させないため、用途を分離した鍵付き指紋も保持します。これらの照合情報は匿名の費用・監査集計とは区別し、平文のClerk主体やメールアドレスを保存しません。照合に必要な旧鍵も保持し、失った鍵を自動生成して置き換えません。

削除済み通知の配信Webhookが遅れて届く場合も、外部配信IDの一方向ハッシュで照合し、削除した外部IDや配信イベントを再保存しません。この照合情報に宛先・通知内容・元ユーザーIDは含めません。

Clerk削除が完了するまで、削除先の認証発行元・ClerkユーザーIDを専用キューへ暗号化して一時保持します。元の内部ユーザーID・メールアドレス・契約データ・APIキーはキューへコピーしません。Clerk APIで削除を確認したら、この暗号化された削除先も消します。

## 実行と障害時

退会の受付と利用停止、削除要求の保存は同じトランザクションで行います。受付後は新規のメール処理やAI呼び出しを開始せず、実行中のWorkerとの競合を制御します。先行する外部処理の終了を待ち、データ削除と費用・監査の移し替えは一つのトランザクションで確定します。途中の失敗では再実行でき、他の所有者のデータは変更しません。

Clerkへの通信はローカル削除の完了後に行います。接続障害・利用制限・設定不足があってもアプリ内の削除を止めず、Clerk削除を再試行します。通常は1分から最大1時間まで待ち時間を延ばし、提供元のRetry-Afterは最大24時間まで尊重します。再起動や応答喪失後も同じ対象を照合し、対象ユーザーが既に存在しなければ完了とします。受付状態はClerk削除も確認できるまで`pending`、両方の削除後に`completed`です。

管理者は「APIキー」でClerk Backend APIのSecret Keyを登録し、「外部連携」で同じClerkインスタンスIDを設定してください。キーは既存の暗号化資格情報管理を使い、環境変数には追加しません。Workerの認証発行元・設定のインスタンスID・Clerk APIが返すインスタンスIDと認証ドメインを毎回確認し、不一致なら削除を実行しません。認証発行元と対象ユーザーは受付時の値を維持し、設定の入力ミスは訂正後に再試行できます。削除Webhookは再照会を早めるために使い、外向き削除の完了はAPIで確認します。既存の完了済み退会に対して、migrationが後から外部削除を実行することはありません。

APIの根拠は[Clerk公式Backend API仕様](https://github.com/clerk/openapi-specs/blob/main/bapi/2026-08-20.yml)です。`GET /instance`と`GET /domains`で対象を確認し、`DELETE /users/{user_id}`でClerkユーザーを削除します。

送信済みの内容を外部プロバイダーから回収する処理や、提供元でのOAuth許可取り消しは行いません。必要に応じてGoogle・Microsoftなどの設定でも連携を解除してください。バックアップ内のデータは通常DBと別に管理するため、復元時にも削除済み主体を再利用しない運用が必要です。

過去にすでに利用停止・削除待ちとなっていたユーザーを、migrationだけで自動削除しません。新しい本人確認済みの退会要求または検証済み削除イベントから処理します。開発・検証は一時schemaと合成データを使い、実ユーザーの退会や外部アカウント削除をテスト目的で実行しません。
