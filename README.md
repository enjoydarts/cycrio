# Cycrio

Cycrio（サイクリオ）は、日本語の請求・更新メールからサブスクリプション情報を整理する、個人利用向けの管理サービスです。

メール原文を永続保存せず、指定期間の過去メールと新着を解析し、サブスクと請求履歴を自動登録します。元のAI抽出値、自動登録した情報、本人が訂正した値を区別し、不明な金額や日付を推定で埋めません。登録した請求履歴を通貨別に集計し、支払日から周期候補を比較し、本人が確認した周期から次回予定を計算できます。

## 開発状況

Docker Composeによる開発環境に、Clerkログイン、利用許可・管理者権限、APIキーの暗号化保存、DBモデルカタログ・価格履歴、AI実行設定・接続テスト・有効化、使用ユーザー別の月次原価、本人のFastmail接続管理、初回の過去メール取り込みと新着の自動解析、サブスクと請求履歴の自動登録・手動訂正、通貨別の月次集計、支払履歴の完全一致による周期候補の比較、確認した周期・基準日からの次回予定計算を実装しています。サービス名の意味を推測した契約の統合や、支払日のずれを許容する周期推定は行いません。

個人利用MVPから始め、将来の商用SaaS化を見据えて所有者分離・管理者権限・AI原価管理を設計します。一般ユーザー向けの公開開始は別途判断します。

## 技術方針

- UI：Svelte 5 / SvelteKit / TypeScript
- フロント配信：Cloudflare Workers Static Assets
- API・バックグラウンド処理：Go（別プロセス）
- 永続化：PostgreSQL
- ジョブ制御：開発はローカルHatchet Lite、本番はHatchet Cloud
- アプリ認証：Clerk（Googleアカウントでのログインのみ）
- アプリからのメール送信：Resend
- メールの一次判定：Liquid AI D1
- メールの二次処理：OpenRouter / OpenAI / Anthropic
- AI設定：管理者専用画面で使用プロバイダー・モデルと各APIキーを設定。AI APIキーは環境変数で供給せず、DBへ暗号化保存
- AI原価：管理者専用画面で月別・使用ユーザー別・プロバイダー別・モデル別に確認

## ローカル起動

必要なものはDocker Engine / Docker Desktop、Docker Compose v2以降、Makeです。Go・Node・npmのホストへのインストールは不要です。

```sh
make up
```

`.env`の作成やHatchetアカウントの準備は不要です。DB初期化・Hatchet起動・Worker接続用トークンの発行・DB外の暗号化鍵の初期生成を自動実行します。初回はイメージ・依存関係の取得とGoビルドに時間がかかります。

| 接続先 | URL |
|---|---|
| Cycrio Web | http://localhost:3100 |
| API readiness | http://localhost:8090/readyz |
| Hatchet管理画面 | http://localhost:8888 |
| Hatchet gRPC | `localhost:7077`（アプリは内部の`hatchet:7077`へ接続） |

Hatchet管理画面の開発用ログインは`admin@example.com` / `Admin123!!`です。アプリのClerkログインとは別です。公開ポートはlocalhostに限定し、DB・Workerのポートはホストに公開しません。ポートを変更する場合のみ`.env.example`を`.env`へコピーして調整してください。

| サービス | 役割 |
|---|---|
| `web` | SvelteKit / Vite。ソース変更はHMRで反映 |
| `api` | Go HTTP API。`/healthz`は生存、`/readyz`はDB接続を確認 |
| `worker` | Hatchetタスク実行。自身のACTIVE状態・heartbeatとDBをreadinessで確認 |
| `postgres` | Cycrio専用DB。管理用・migration用・実行用ロールを分離 |
| `hatchet` | Hatchet LiteのAPI・Engine・管理画面 |
| `hatchet-postgres` | Hatchet専用DBとメッセージキュー |
| `hatchet-init` | 初回の接続トークン発行。正常終了後は停止状態でよい |
| `keyring-init` | migration後、暗号化鍵を初回だけ生成。既存の鍵は保持。正常終了後は停止状態でよい |
| `devcheck` | `make smoke`から起動する疎通確認CLI |

Clerkは次の手順で開発用アカウントへ接続します。起動・通常の疎通確認では外部AIを呼び出しません。管理画面からの接続テストは明示的な課金確認後に実行します。Resendによる本人宛ての固定テストメールは、管理者の明示操作で送信できます。

## 初期ログイン設定

1. Cycrio専用のClerk開発インスタンスを作成し、Google接続だけを有効にします。メールOTP・パスワード・電話・他のSNS接続はClerk側でも無効にしてください。
2. `make up` の後に `make configure-auth` を実行し、Clerkの **Publishable Key** とフロントのorigin（通常 `http://localhost:3100`）を入力します。Secret Keyは入力しません。
3. Webを開いてGoogleでログインします。初回は利用許可待ちとなり、本人のClerkユーザーIDが表示されます。
4. 運用者が `make grant-admin USER_ID=user_...` を実行して、対象者を初期管理者として許可します。利用許可を再確認するとアプリを利用でき、設定に管理者専用の項目が表示されます。

初期公開設定はGit対象外の`.local/bootstrap.json`へ保存されます。セッション検証は設定済みClerkインスタンスの公開JWKSを使い、APIはClerkのSecret Keyを要求しません。認証未設定でも開発環境は起動しますが、保護されたAPIは利用できません。GoogleログインはGmail取得の許可を意味しません。

一般利用者の許可は`make allow-user USER_ID=user_...`、管理者権限の解除は`make revoke-admin USER_ID=user_...`、利用停止は`make disable-user USER_ID=user_...`です。最初にアクセスした人を自動で管理者にする仕組みや、認証を省略する開発用ログインはありません。許可済みユーザーの状態・権限は毎APIリクエストでDBから確認します。

## アプリの使い方

ログイン後は「ホーム」「サブスク」「メール解析」「設定」の共通ナビから操作します。PCでは1本のサイドナビ内に設定項目を展開し、個人設定と管理者設定を分けて表示します。スマートフォンでは下部ナビの「設定」から設定一覧を開き、各ページの「設定一覧に戻る」で戻れます。設定は項目ごとにURLを持ち、通常利用時に接続フォームや管理者の設定を開く必要はありません。

| 画面 | URL | 主な操作 |
|---|---|---|
| ホーム | `/` | 保存済みの請求日・要対応件数・メール連携状態・当月の支払/返金実績 |
| サブスク | `/subscriptions` | 登録済み契約の検索・状態別表示・追加・詳細編集 |
| 請求履歴 | `/subscriptions/{id}?tab=history` | 契約ごとの請求情報・支払・返金と登録の由来・出典 |
| 月次集計 | `/subscriptions/summary` | 登録済み明細の月別・契約別・通貨別集計 |
| メール解析 | `/analysis` | 自動処理の開始・停止・再開、最近の結果と要対応項目・実行履歴 |
| メール連携 | `/settings/mail` | 本人の接続の追加・更新・接続確認・フォルダー選択・ID同期 |
| 表示 | `/settings/appearance` | ライト・ダーク・端末に合わせる配色の選択 |
| AI モデル | `/settings/ai-models` | 管理者による一次・二次モデルの選択 |
| AI 実行・接続 | `/settings/ai-runtime` | 管理者による実行制限・接続テスト・有効化 |
| メール解析の送信条件 | `/settings/mail-policy` | 管理者によるAIへの送信許可と保持条件の確認 |
| APIキー | `/settings/credentials` | 管理者による秘密値の登録・更新・無効化 |
| メール送信・外部イベント | `/settings/integrations` | 管理者本人へのテスト送信、Clerk同期・停止反映、配信結果の確認 |
| モデルカタログ | `/settings/catalog` | 管理者によるモデル・価格履歴の管理 |
| AI利用原価 | `/settings/usage` | 管理者による月別・使用ユーザー別の原価確認 |

サブスクが未登録の場合は、メール連携・送信条件・取り込み状況に応じた初回案内を表示します。複数接続は対象を選んで確認できます。案内は状態の読取だけを行い、取り込み開始や本文送信の同意はメール解析画面で確認します。「一覧を更新」で登録結果と要対応件数を読み直せます。検索0件は条件解除、範囲外のページは先頭へ戻る案内と区別します。

旧URLの`/mail`と`/admin`は新しい設定画面への入口として保持します。一般利用者には管理者項目を表示せず、管理APIも権限を確認します。

### サブスクの登録と確認

ホームは本人のデータを`GET /v1/overview`でまとめて読み取ります。今日から30暦日（日本時間・今日を含む）の保存済み次回日を日付順に最大10件表示し、対象の全件数、日付超過・未設定の件数も示します。対象は利用中・状態不明の契約で、終了済みを除きます。日付や登録料金を新しい請求予測・引落確定額へ変更せず、閲覧だけで契約を更新しません。

当月の実績は、月次集計と同じ保存済み支払・返金明細の計算です。終了済み契約も含め、通貨別に扱います。ホームの月・日付範囲・件数は同じ取得時刻とDB snapshotを基準とし、月額換算や為替換算は行いません。更新ボタンで全体を読み直せます。取り込み開始・送信同意・再開は引き続きメール解析画面で行います。

自動登録を有効にすると、保存済みの抽出イベントからサブスクを作成し、明確に一致する既存契約へ紐付けます。サービス名とプランを保守的に比較し、通貨が相反する場合や候補が複数ある場合は要対応とします。金額が変わっただけで同じ契約を量産せず、同じ抽出イベントの登録を繰り返しません。「サブスク」からの手動追加や、例外イベントの登録・紐付けもできます。

自動作成した契約の利用状態は「状態不明」です。取引総額を定期料金へコピーしません。明示された日付に基づく新しい次回日・周期だけを反映し、古いメールで新しい情報を巻き戻しません。本人が契約を編集した後は自動で値を上書きせず、元メールの根拠を追加します。抽出が0件の場合は登録対象なしと表示し、登録操作を求めません。

契約のサービス名・プラン・料金と通貨・周期・次回請求日・利用状態を編集できます。料金や日付の未設定は0円や推定日に置き換えません。支払額と定期料金が一致するかを確認し、メールにない周期や将来日付を自動補完しません。料金は小数文字列として保持し、通貨を混ぜた合計は表示しません。

自動登録と本人による登録・訂正の由来を保持し、元のAI抽出イベントは別に保存します。契約を編集しても元の抽出情報は変更しません。登録に使った過去の解析結果も契約詳細から確認できます。古いversionからの更新は競合として拒否し、入力内容を確認してから最新状態へ切り替えます。

### 請求履歴と月次集計

自動登録が有効な場合は、契約に紐付いた解析イベントのうち、取引日・金額・通貨が揃う請求情報・支払をその種別のまま履歴へ記録します。返金は返金可能な元支払が一意に定まる場合だけ記録します。不足・重複候補・返金対象不明は要対応とし、勝手に合計へ加えません。契約詳細からの手動記録・訂正もできます。不明な金額を0円、取引日を受信日や次回請求日で補完しません。履歴の登録で契約料金・周期・次回請求日を自動変更しません。

請求情報は支払済みとは扱いません。同一契約の種別・取引日・数値金額・通貨が一致する場合は、同じ取引の可能性を確認します。別の通知だった場合は既存明細へ出典を追加でき、別取引として記録する場合は明示的な確認が必要です。同一の抽出イベントを複数明細へ重複利用できません。誤った出典は紐付けを外して訂正できますが、元のAI抽出値と契約への参照は保持します。

返金は同じ契約・通貨の元支払を選びます。部分返金を複数記録できますが、有効な返金合計が元支払額を超える操作は拒否します。返金済みの支払を減額・除外するなど、既存返金と矛盾する訂正も拒否します。明細の除外はアプリ内の集計対象から外す操作であり、サービス側の支払や返金を実行しません。訂正・除外・出典変更は版管理され、過去の記録を保持します。

自動記録した明細と本人が記録・訂正した明細の由来は区別します。誤った出典の紐付けを解除すると、自動処理が勝手に復活させません。既存明細や過去の訂正前の事実と重なる別メールは、重複候補として扱います。

「月次集計」は登録済みの有効な明細を対象とし、当月1日以上・翌月1日未満の取引日で支払額・返金額・差引額と件数を通貨別に表示します。初期月は日本時間で選び、返金は返金日の月に計上します。請求情報と除外済み明細は支出へ加算せず、記録なしと記録済み0円を区別します。通貨の合算・為替換算・月額換算・将来予測は行いません。通常の履歴操作でメール取得や有料AI呼び出しは発生しません。

### 次回予定の計算

契約詳細の「次回予定を計算」から、N日・N週間・Nか月・N年の周期と基準請求日を確認して候補日を計算できます。月・年の周期では日付指定と月末固定を選びます。月末固定の基準日は月の最終日を選んでください。

各回を元の基準日から計算し、その月に同じ日付がなければ月末へ丸めます。1月31日の毎月契約は2月28日へ丸めても3月31日に戻り、2月29日の年次契約は非閏年に2月末、閏年に2月29日へ戻ります。28日周期と毎月は異なる規則です。候補は日本時間の当日以降で最初の予定日です。

計算と保存は別操作です。候補と既存次回日を確認して保存すると、周期・元の基準日・次回日を一緒に記録します。既存の料金・プランや支払履歴は更新しません。画面を開いたことや日付の経過だけで契約の次回日を変更せず、過ぎた予定日を支払済みとは扱いません。終了済み契約では候補の採用を停止します。

通常の契約編集で周期を変更した場合や、終了済みから利用中へ戻した場合は基準日を再確認します。料金だけを変更しても計算条件は維持します。手動で訂正した次回日を計算値で自動的に戻しません。古い版や日付が変わったプレビューは再確認が必要です。受付状況が不明な保存は同じ要求で確認し、保存後の手動訂正へ古い要求を再適用しません。

### 支払履歴からの周期候補

「次回予定を計算」の中から「支払履歴から候補を確認」を開き、対象開始日と通貨を指定します。プランや契約条件に変更があった場合は、変更後の開始日を選んでください。登録済みの有効な支払のうち、直近最大5件の日付から周期を比較します。最低3件の異なる日付が必要です。

日付が完全に一致する固定日数と月・年の規則を比較し、28日ごとと毎月を区別します。月末や閏年で将来の日付が異なる場合は複数候補を表示します。決済日のずれは許容せず、履歴不足・同日複数・不規則な場合は一つに決めません。記録間隔の候補であり、未記録の支払や実際の契約周期を保証するものではありません。

請求情報・返金・除外済み・未来の明細はサンプルに含めず、有効な返金がある支払も部分返金を含めて除外します。0円の記録済み支払は含め、通貨を混ぜません。周期候補の比較で走査対象が1000件を超える場合は期間を絞ってください。この上限はメールの自動取り込み件数とは別です。

候補を選ぶと計算条件への入力だけを行います。日付の計算と確認保存は別操作です。保存前に履歴が変わった場合は候補を確認し直し、手動編集した周期や次回日を自動更新しません。保存時の根拠は履歴の後の訂正と分けて保持します。通常の確認でメール取得・AI呼び出しは発生しません。

## 自分のFastmail連携

利用許可済みのユーザーは、「設定」→「メール連携」（`/settings/mail`）から、自分の接続を設定できます。接続一覧から追加・詳細へ進みます。管理者も自分の接続だけを扱います。ClerkのGoogleログインと、メール取得用の資格情報は別です。

1. 「Fastmail を追加」を選び、表示名・Fastmailの完全なログインメールアドレス・メール利用を許可した専用アプリパスワードを入力して保存します。通常のFastmailパスワードは使いません。
2. 「接続を確認する」を押します。Workerが固定の`imap.fastmail.com:993`へ暗黙TLSで接続し、認証とフォルダー一覧取得だけを行います。保存だけでは接続しません。
3. 対象フォルダーを選んで「フォルダー選択を保存」を押します。名前で絞り込んでも表示外の選択は保持します。選択不可（NoSelect）や取得不能のフォルダーは選べません。選択なしでも保存できます。

この段階では、フォルダーを保存してもメール同期・本文取得・既読化・AI送信を開始しません。接続確認は明示操作でだけ実行します。受付結果が不明な場合の「同じ接続確認を再送する」は同じ要求IDを使い、重複作成を防ぎます。

ログイン名とアプリパスワードは所有者・接続・資格情報版を束縛してDBに暗号化保存し、保存後は再表示しません。接続情報を更新すると以前の確認結果と選択をリセットします。連携解除は確認後に行い、過去の資格情報と進行中の要求も無効化します。再接続には新しい値を入力してください。古い画面からの更新は競合として拒否し、通常の再読み込みでは編集中入力を保持します。

接続は本人ごとに最大10件。確認処理には30秒・応答1MiB・1000フォルダーの上限があります。認証拒否・TLS失敗・時間切れ等は固定の理由で表示し、生のサーバー応答を保存・表示しません。実アカウントでの確認にはIMAP対応プランと専用アプリパスワードが必要です。[Fastmail公式設定](https://www.fastmail.help/hc/en-us/articles/1500000278342-Server-names-and-ports)

### メールIDの手動同期

接続確認とフォルダー選択を保存した後、同じ画面で開始日・終了日・最大件数を入力して明示実行します。日付はメールサーバーの受信日の暦日条件で、開始日を含み、終了日を含みません。指定できる期間は1〜366日、最大件数は1〜1000件です。

この操作は選択フォルダーを読み取り専用で開き、対象のメールIDを列挙します。本文・件名・送信者の取得、既読化、AI送信は行いません。取得参照は暗号化して保存し、画面には今回確認したID数と、新しく台帳へ追加した件数を分けて表示します。履歴は最新20件です。

上限到達は「列挙完了」と区別します。同じ期間で改めて実行すると、保存済みカーソルから続けます。期間を変えると別の走査範囲となり、既に登録したIDは新規追加に数えません。IMAPのUID世代が変わった場合は新しい世代として列挙します。

停止・接続情報の変更・連携解除・利用停止後は、古い処理の結果を保存しません。失敗や中止後の再開は明示操作で行います。受付結果が不明な場合は、同じ要求を再送して重複開始を防ぎます。

### 過去メールと新着の自動解析

「設定」の準備状況で、メール連携・AI接続・本文送信許可と、次に必要な操作を確認できます。管理者は「AI の準備・送信許可」（`/settings/ai`）でモデル選択、接続テスト、有効化、送信条件の確認を順に進めます。接続確認済みの有効版がある場合は、その構成に対する送信許可から続けられます。モデル構成を変更した場合は、新しい構成で条件を確認し直します。APIキーは管理者の暗号化設定を使います。

本人は「メール解析」で接続と初回の対象期間を選び、対象フォルダー、本文全体の送信、モデル・実配信先、保持条件、出力・待機上限、参考料金を確認して自動処理を開始します。初期期間は日本時間の過去1年で変更できます。継続する新着の解析と自動登録に一度同意し、バッチごとの開始操作は不要です。自動登録を有効にすると、他の接続を含む保存済み解析結果も対象になります。条件の保存や画面の読み込みだけでは開始しません。価格不明は不明と表示し、確定費用や課金上限として扱いません。

初回の対象メールを全件走査しながら、5分ごとに新着を確認します。対象期間は開始日を含み、終了境界日を含まない日本時間の範囲です。ID探索の1000件・解析の100件は一回の作業単位であり、残りは保存した位置から続けます。取り込み中もアプリを閉じられ、再起動後も進捗を引き継ぎます。履歴と新着の処理を交互に進め、対象外候補や空のページが続いても新着を待たせ続けません。

同意できない場合は、チェック欄の近くに不足している準備と操作先を表示します。管理者は送信許可やAI設定へ進み、対象の接続・件数・絞り込みを保持して解析へ戻れます。戻った後は最新条件を読み直し、今回の外部送信への同意を新しく行います。一般ユーザーには管理者の準備が必要な状態を案内し、管理APIや管理者用の設定は公開しません。

Workerは1通ずつ読み取り専用で本文パートを取得し、Liquid AI D1で一次判定します。関連あり・判定不確実のメールを二次AIへ送り、検証したサービス・金額・通貨・日付等を本人の解析結果として保存します。本文全体モードでは独自の8KiB等の本文上限を使わず、正規化した本文全体を渡します。分割による追加AI呼び出しや、黙った切り捨ては行いません。原文・正規化本文・モデルの自由応答はDB・Hatchet・ログへ保存しません。添付・埋め込みメールは取得対象から除き、HTMLの外部リソースも読み込みません。既存の通信総量5MiBやMIME構造等の受信保護は維持し、取得不能や解釈できない本文を成功扱いにしません。

本文全体の送信には管理者の許可が必要です。既存の有効モデルで送信範囲だけ変更する場合、有料接続テストのやり直しは不要です。以前に受け付けた手動解析は保存済みの入力上限・送信条件を保持し、新しい全文要求へ勝手に切り替えません。

解析結果と実行履歴は接続を横断してページングし、総件数と続きを表示します。結果はメールごとの最新終了試行が対象で、登録済み結果・要対応・処理状態で絞り込めます。通常の停止・再開では対象期間・世代・進捗を引き継ぎます。利用停止・接続更新・有効なAI構成や送信条件の変更・メールUID世代の変更では自動送信を止め、必要な条件を確認し直します。送信済みの呼出しには料金が発生する場合があり、その原価は停止後もメール所有者へ紐付けて記録します。

失敗・結果不明のメールは自動で有料再送せず、結果ごとの再解析で確認してから再送します。旧本文上限で失敗し、過去の全試行でAIを一度も呼んでいない対象メールだけは、新しい全文送信への同意後に一度回復します。結果不明の再解析には、重複処理・再課金の可能性の追加確認が必要です。本文送信を伴わないID探索の一時的な接続失敗だけは、保存位置から有限回再試行します。受付不明時の再送は同じ要求ID・条件を使い、設定競合では編集中の入力と元の条件を保持します。

手動のID同期・件数指定解析も詳細操作として利用できます。周期の推定候補の採用や、手動で訂正した値の置き換えは本人の確認を必要とし、自動登録で勝手に採用しません。

## 管理者のAPIキー設定

1. 管理者としてGoogleログインし、「設定」→「APIキー」（`/settings/credentials`）を開きます。
2. Liquid AI（D1）、OpenRouter、OpenAI、Anthropic、Resendのうち、利用するサービスのキーを入力して登録します。未使用サービスへの登録は不要です。
3. 変更するときは新しいキーを入力して更新します。保存済みの値は再表示できません。無効化すると、そのサービスの過去のキーも内部利用できなくなります。

画面に表示するのは登録状態、更新日時、版番号と最新50件の操作履歴です。APIキーの環境変数・URL・ブラウザー保存領域での設定経路はありません。入力は保存操作後に消去します。古い画面から更新した場合は競合として拒否し、再読み込み後に操作します。管理APIも毎回DBの現在の管理者権限を確認します。

キー登録はプロバイダーへの推論接続成功を意味しません。キーの登録・更新だけで有料推論やResend送信は行いません。

## モデルカタログと価格

管理者はAI設定で一次のLiquid AI D1と二次モデルを選びます。価格が不明なモデルは、選択したモデルの近くにある「価格を設定」から入力・出力の100万トークン当たり単価、リクエスト単価、通貨、出典、適用開始日時を保存できます。キャッシュ料金は詳細項目です。空欄は不明、`0`は明示的なゼロとして区別します。現在の参照価格と有効版に固定した価格を分けて表示し、価格の保存だけで有効版や過去の実利用原価を変更しません。

モデルカタログではモデル検索・追加・編集・利用候補への指定・価格履歴を管理します。モデルIDの自由入力はカタログ保守に限定し、設定の保存時にはカタログの内部IDと価格版を固定します。

| プロバイダー | 自動取得 | 手動で扱う項目 |
|---|---|---|
| OpenRouter | 公開Models APIのモデル情報・価格・対応パラメーター | 表示名・有効/無効・価格の上書き |
| OpenAI | 登録済みAPIキーでModels APIのモデル情報 | APIにない能力情報・価格 |
| Anthropic | 登録済みAPIキーでModels APIのモデル情報・能力・上限 | 価格。キーの種類に応じてWorkspace IDも管理画面で設定 |
| Liquid AI | 公開カタログAPIを確認できないため自動取得なし | モデル・能力・価格。初期モデルは指定済みの`d1`だけ、価格は未設定 |

OpenRouterのModels API同期はAPIキーを要求しません。OpenAI・AnthropicのキーはAPIキー管理画面で登録します。自動同期の既定間隔は24時間で、管理画面から1〜168時間への変更・停止・手動同期ができます。取得結果はDBへ保存し、Hatchet Workerで処理します。キー未登録や取得失敗は同期状態へ表示し、アプリの起動を止めません。

全ページの取得・検証が成功した場合だけカタログを更新します。APIから消えたモデルは履歴を残して取得不能とし、手動モデルや管理者による表示名・有効/無効・価格上書きは保持します。価格が変わったときは新しい版を作り、過去の設定の価格参照は変更しません。手動価格から最新API価格へ戻す操作もできます。

料金は十進数の文字列で保存し、入力/出力/cacheのtoken料金、request・画像・検索単価を区別します。OpenRouterの条件別料金・割引・将来追加される価格項目も元データとして保持します。欠落や変動料金を0円として扱いません。OpenRouterのカタログ価格は参考値であり、実際の配信先の原価を保証するものではありません。カタログ同期・モデル選択の保存は、推論の接続確認や有効化とは別の操作です。

自動取得範囲は[OpenRouter Models API](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties)、[OpenAI Models API](https://developers.openai.com/api/reference/resources/models/methods/list)、[Anthropic Models API](https://platform.claude.com/docs/en/api/models/list)の公開仕様に基づきます。価格APIが公開契約にないサービスはHTMLスクレイピングへ切り替えません。

## AI実行設定と接続テスト

管理者は「設定」→「AI の準備・送信許可」で次の順に操作します。以前のAIモデル・実行設定・送信条件のURLからも、同じフローの該当段階を開けます。

1. 「モデル・料金」で一次・二次モデルを選びます。OpenRouterはZDR・構造化出力・入出力上限などの条件を満たす配信先を照合し、適合する候補だけを表示します。実配信先と参考価格を確認し、必要なら価格を設定します。保持・学習利用条件を個別確認するOpenAI / Anthropicの直接接続も選べます。
2. 「モデルと実行設定を保存」で、モデル・価格・APIキー版と配信先の確認結果を不変の下書きへ固定します。出力・待機上限や従来の手動解析・接続確認の入力基準は詳細から変更できます。新しい下書きの保存後も、以前の有効版は明示的な切替えまで保持します。
3. テスト送信・課金を確認し「料金を確認して接続テスト」を押します。サーバー固定の合成メールで一次判定と構造化抽出を最大2回呼び出します。メール原文・生成本文・秘密値は台帳やHatchetへ保存しません。一次・二次の結果を別々に表示し、認証拒否・支払条件・モデルや配信先の利用不可・利用制限には安全な案内を表示します。
4. 同じ下書きのテスト成功後に「成功したテストの版を有効化」を押します。有効版の停止も明示操作で行います。
5. 「送信許可」で本文全体の送信範囲と一次・二次の保持・学習利用条件を確認します。一次はLiquid AI標準規約または個別契約を選択し、二次OpenRouterは有効版と一致する配信先のZDR確認結果を表示します。両方の条件を新しく確認して本文送信を許可し、解析画面で初回期間と継続処理に同意します。

配信先情報は、登録済みOpenRouterキーをサーバーで解決して[公式ZDR一覧](https://openrouter.ai/docs/api/api-reference/endpoints/list-endpoints-zdr)からまとめて取得します。AI設定で情報が未取得・期限切れの場合は無料で照合し、モデルの選択時には実際の配信先を表示します。新しい保存には15分未満の情報と現在のキーを使います。情報の取得失敗では以前の記録を保持し、時間が経過しただけでは既存の有効版や送信許可を停止しません。最新の完全な照合で非適合が確認された場合や、編集中の配信先が消えた場合は、別社へ黙って切り替えず確認・選び直しを求めます。選択した配信先の価格とモデル全体のカタログ参考価格も区別します。

[Liquid AI標準規約（2026-09-30版）](https://www.liquid.ai/terms-conditions)では、提供コンテンツの保持や学習・評価・改善への利用が認められ、固定の保持日数は示されていません。D1の標準条件をZDRとして扱いません。個別契約の条件は管理者が記録し、規約の版・構成・条件を変更した場合は再確認します。確認時の条件・配信先・公式出典を証跡として保存し、一般ユーザーの解析画面にも出典リンクを表示します。

通信結果が不明なテストは自動再実行しません。受付応答だけを受け取れなかった場合は「同じテスト要求の受付を確認」で重複実行を防ぎます。追加の有料テストは改めて確認して開始します。APIキー更新後は、画面の案内に従って実行設定を再保存し、接続テスト・有効化を行います。既に開始した処理は固定した旧キー版を使いますが、無効化されたキーは利用しません。

OpenRouterは指定モデルと承認配信先を固定し、フォールバック禁止・データ収集拒否・ZDR必須・応答キャッシュ無効で呼び出します。条件を満たす配信先がない場合は失敗として記録します。有効化は将来のメール処理が使う設定の準備であり、この段階ではメール収集や定期推論を開始しません。

## 月次・使用ユーザー別のAI原価

「設定」→「AI利用原価」で、JSTの月初以上・翌月初未満に開始した呼出しを集計します。実際の消費利用者と操作した管理者を分け、接続テストは`admin_test`、システム処理は`system`として利用者の原価と分けて表示します。プロバイダー・モデル・処理段階・利用者・スコープで絞り込めます。呼出し0件の利用者も確認できます。

金額は十進数文字列で保存・表示し、通貨を混ぜません。OpenRouterは取得できた利用料金報告を採用し、それ以外は固定した価格版と使用量から安全に計算できる範囲で推定します。未取得・不明・未対応の料金条件は不明とし、0として扱いません。失敗した呼出しも課金・不明件数を残します。

OpenRouterの「原価を再照合」は保存済み生成IDの料金取得だけを行い、推論は再実行しません。報告額は推定額を置き換え、版履歴を合計へ重ねて加算しません。月次額は後から変わる暫定集計です。上流には料金訂正の順序を示す時刻がないため、過去に採用した金額への再変更と古い応答の再送を区別できません。現在は過去額の再報告を履歴へ残し、最新採用額を維持します。商用請求の確定額として扱う機能は未実装です。

## メール送信・外部イベントの設定

「設定」→「メール送信・外部イベント」で、Resendの接続確認と署名付きWebhookを設定します。任意宛先や本文を入力する機能、定期通知はありません。

1. 「API キー」でResend APIキーと、Clerk / Resendの各Webhook署名鍵（`whsec_...`）を登録します。秘密値は既存の資格情報管理で暗号化保存し、保存後は平文表示しません。ClerkのSecret API Keyは不要です。
2. Resendで利用できる送信元メールアドレスと、ClerkのインスタンスID（`ins_...`）を保存します。Clerkのissuerはログイン用bootstrap設定から固定し、他インスタンスのイベントを受け入れません。
3. 外部サービスから到達できるAPIのURLに、Clerkは `/v1/webhooks/clerk`、Resendは `/v1/webhooks/resend` を登録します。localhostへ外部サービスから直接配信はできません。開発用トンネルや公開APIは利用者が別途準備してください。アプリが自動公開することはありません。
4. Clerkは `user.created` / `user.updated` / `user.deleted`、Resendは `email.sent` / `email.delivered` / `email.bounced` / `email.complained` / `email.failed` / `email.suppressed` / `email.delivery_delayed` を選びます。署名鍵は登録先エンドポイントと一致させます。
5. 本人のClerkプロフィールを更新して新しい `user.updated` を発生させるか、既存の本人イベントを再配信します。署名検証済みの確認済みprimary emailだけを暗号化保存し、管理者の送信先に使います。アドレスの平文は管理APIへ返しません。未知利用者のイベントでアプリの利用許可や管理者権限は付与しません。
6. 準備状況を再確認し、本人宛て送信とResend利用枠の消費に同意して「テストメールを1通送信」を押します。件名・本文は固定です。送信受付と受信サーバーへの配信、配信拒否・迷惑メール報告は別々に表示します。

Webhookはraw bodyの署名・時刻を確認してから反映し、全文は保存しません。Clerkはオブジェクト更新日時とイベント日時から新旧を判定し、削除は終端状態として扱います。ban・deprovision・削除は既存ユーザーのAPI利用とメール処理を停止します。解除イベントで利用許可を自動復活させず、送信済みAI呼出しの原価は元の利用者に記録します。

Webhookには遅延があります。アプリは最新の受信済み状態を表示し、外部サービスの現時点と一致することを保証しません。ClerkのインスタンスIDを変更すると同期済み宛先を無効化します。変更後は、同じイベントの再配信だけでは復旧しない場合があるため、新しい `user.updated` を発生させてください。

送信要求はDBへ記録してからResendへ送ります。同じ要求IDでは二重送信せず、結果不明でも自動再送しません。Resendの冪等保証期間（24時間）を過ぎても同じ要求を再送しません。通信エラー時は画面の「同じ送信要求の結果を再確認」を使ってください。「別のテストメールを送る準備をする」は新しい要求を作り、再度の明示確認で別メールを送ります。結果不明のメールも後で届く可能性があります。受付応答から送信IDを取得できなかった場合、配信Webhookだけではその要求の結果を特定できないことがあります。

今回の実装検証は合成HTTP応答・署名付きイベントで行います。実Resend送信、外部Webhook配信、DNS設定、トンネル公開の確認とは区別してください。

公式仕様：[Resend冪等キー](https://resend.com/docs/dashboard/emails/idempotency-keys)、[Webhook署名検証](https://resend.com/docs/dashboard/webhooks/verify-webhooks-requests)、[Clerk Webhook](https://clerk.com/docs/guides/development/webhooks/overview)。

## 暗号化鍵の保管・復元

ローカルの暗号化鍵はGit対象外の`.local/secrets/keyring.json`です。APIキーとメール接続情報はAES-256-GCMで暗号化してDBに保存し、用途・所有者・接続・資格情報ID・版番号等を認証データへ束縛します。Go標準の[ランダムnonce付きGCM](https://pkg.go.dev/crypto/cipher#NewGCMWithRandomNonce)を使用します。DB更新と秘密を含まない監査履歴は同時に保存します。

鍵ファイルは通常の再起動や`make up`で変わりません。**DBのバックアップとは別に、鍵ファイルもアクセス制限した場所へバックアップしてください。** `.local/`を消すとDBのvolumeだけが残る場合があります。暗号化済みの資格情報があるのに鍵を失った場合、初期化処理は新しい鍵を作らず停止します。元の鍵を同じ場所へ復元し、権限を`0600`または`0400`にしてから`make up`を再実行してください。APIキーを登録し直すだけで失った鍵の暗号文を復号できるようにはなりません。

鍵の更新は、旧鍵を`keys`に保持したまま、新しいランダム32バイト鍵を一意のIDで追加して`active_key_id`を変更し、APIとWorkerを再起動します。ファイル形式は`{"active_key_id":"key-id","keys":{"key-id":"base64-encoded-32-byte-key"}}`です。旧暗号文の再暗号化・旧鍵の削除は、この段階では自動実行しません。旧鍵を使うデータが残っている間は、その鍵を削除しないでください。APIキーの通常更新と、暗号化鍵の更新は別の操作です。

Clerk設定の公式手順：[Google接続](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/google)、[公開鍵によるJWT検証](https://clerk.com/docs/guides/sessions/manual-jwt-verification)。実際のGoogleログイン確認には本人のClerk設定が必要です。

## 開発・検証コマンド

全ての言語ツールはDocker Compose内で実行します。

| コマンド | 内容 |
|---|---|
| `make up` | 全サービスをビルドして起動し、healthyになるまで待機 |
| `make down` | 停止・コンテナ削除。DB・Hatchet設定のvolumeは保持 |
| `make ps` / `make logs` | 起動状態 / ログを確認 |
| `make restart` | API・Workerをソースから再ビルドして再起動 |
| `make check` | Goテスト・vet、Webテスト・型検査・整形検査・静的ビルド |
| `make test-integration` | 一時schemaでmigration・認可・秘密管理・AI原価・メール接続・契約登録と解析一覧をDB/API検証 |
| `make test-evaluation-smoke` | 合成30通の本文正規化・解析・契約/請求登録、処理途中の停止、機密値残存検出を検証 |
| `make test-evaluation` | 合成3,000通を含む評価を実行し、metadataだけのJSONをGit対象外の`.local/evaluation/`へ保存 |
| `make test-evaluation-hatchet` | 一時Workerで合成10通をHatchet経由で処理し、アプリDB・Hatchet履歴・評価中のログを検査 |
| `make smoke` | API・Web疎通と、Hatchet経由でのWorker実行・DB接続 |
| `make fmt` | Go / TypeScript / Svelteを整形 |
| `make db-shell` | migration用ロールでアプリDBへ接続 |
| `make hatchet-token` | 開発用Hatchet接続トークンを更新し、API・Workerを再起動 |
| `make build-production` | 本番用GoランタイムイメージとWeb静的成果物をビルド |
| `make preview-static` | 静的成果物をCloudflareローカルランタイムで配信（http://localhost:3199） |
| `make configure-auth` | Clerk公開設定を対話入力してAPIを再起動 |
| `make init-keyring` | 暗号化鍵を初回生成、または既存鍵を検証。通常は`make up`から自動実行 |

Goの特定テストを実行する例：

```sh
docker compose run --rm --no-deps api go test ./internal/health -v
```

機能追加・不具合修正はTDDで進め、失敗するテストの確認→実装→成功確認→リファクタリングの順に作業します。Compose等の設定変更は構文・ビルド・起動・再起動を検証します。

合成評価は`make up`後に実行してください。一時schema・一時鍵とメモリ内のメール/AIアダプターを使い、外部通信や有料AI呼出しを行いません。実際の処理サービス、所有者別DB台帳、自動契約・請求登録を通します。10通ごとに正常支払6・無関係1・無効抽出1・AI結果不明1・本文取得失敗1を投入し、結果不明になったバッチの未送信分だけを次の明示要求で処理します。重複leaseと登録の再実行で重複が生じないことも確認します。

JSONの`synthetic_costs`はアダプターが返す合成金額で、実料金ではありません。不明原価は金額を`null`、件数を`unknown_calls`として残します。時間は直接leaseを実行した所要時間です。本文・疑似秘密の検出文字列は、一時schemaの全行、lease JSON、画面向け結果JSONについて生文字・hex・単独base64を検査します。任意の変換後の値、実Hatchetの履歴、Dockerログを網羅する検査ではありません。実Googleログイン・IMAP通信・AI精度/実原価・Hatchet配信/保存・外部Webhook・実利用者UIは未確認としてJSONに明記します。

`make test-evaluation-hatchet`は別の追加評価です。通常Workerへの評価モード追加や外部AI接続は行わず、既存ローカルHatchetに一意な名前の一時Worker/taskを登録します。leaseのみを配送し、成功6・無関係1・失敗2・結果不明1、重複leaseの再配送を確認します。Hatchetの実行履歴には合成metadataが残ります。Hatchet DBのpublicテーブルをread-only snapshotで検査し、各評価run IDが実際に保存されたことも確認します。

結果は`.local/evaluation/hatchet-*/`に保存されます。`hatchet-report.json`が配送・DB検査、`evaluation_worker-check.json`が評価コンテナの標準出力/標準エラー、`docker_services-check.json`が評価開始以降に取得したapi/worker/hatchetのDockerログの検査結果です。全て成功した場合だけ`complete.json`が作られます。probe manifestと生ログを含むため、ディレクトリは0700、ファイルは0600とし、共有・コミットしないでください。検出時は値を表示せず失敗します。

この検査も生文字・hex・単独base64の範囲です。ローカルの取得時点の履歴/ログを対象とし、取得後の遅延ログ、Hatchet Cloud、外部payload storage、通常Workerのdispatch loop全体は未確認です。実IMAP・実AIの精度/料金も対象外です。

ログ取得前後に対象3サービスが起動していることを確認し、取得コマンド自体の失敗は評価失敗にします。対象期間にログがなければ、Dockerログの結果には`bytes: 0`・`empty: true`を記録します。評価コンテナ自身の出力は空なら失敗します。

同じコマンドで、中断評価も行います。一次AIの応答待ち中に処理停止・接続切断・Clerkユーザー削除を行い、遅延原価を保持しながら二次AI・抽出採用・契約/請求登録へ進まないことを確認します。ユーザー削除は`user.deleted`を受けた既存の`deleting`状態とtombstoneを対象とし、メール接続や利用者データの物理消去を検証したとは扱いません。

強制停止では、一時schemaと一時鍵を参照する評価専用Workerを子プロセスで動かし、合成AI要求が到達した後にそのプロセスだけをSIGKILLします。アプリのlease期限は一時schema内だけで進めて回収し、別Workerへ古いleaseを配送してもAIを再呼出ししないことを確認します。期限切れの呼出しは台帳でも`unknown`へ確定し、不明原価を0へ変えません。後から届く原価情報は引き続き記録できます。実時間で6分待つ試験や、通常Worker/エンジン全体のfailover・強制停止と切断/削除が重なる複合障害は未確認です。

中断4ケースの結果は同じディレクトリの`interruptions-report.json`へ保存します。子プロセスのstdout/stderrも既存ログ検査に含めます。子プロセス設定は一時DBへの接続情報と一時鍵のパス等を含むため、他の評価artifactと同様に非公開で扱ってください。

## 構成と永続化

```text
cmd/api/          HTTP API
cmd/worker/       Hatchet Worker
cmd/devcheck/     実ジョブによる疎通確認
internal/        共通処理と *_test.go
web/             SvelteKit、静的配信設定
deploy/docker/   Goの開発・本番Dockerfile
deploy/local/    開発DB・Hatchet初期化とGo起動処理
cmd/manage/      migration・初期ログイン設定・利用許可の運用CLI
```

アプリDB、Hatchet DB、Hatchetの署名・暗号設定、接続トークンは別々のnamed volumeへ保存します。アプリの暗号化鍵はvolumeとは別の`.local/secrets/keyring.json`です。GoキャッシュとWeb依存もvolumeで再利用します。`docker compose down --volumes`はvolume内のデータを削除するため、データを消す意図があるときだけ使用してください。

DBコンテナにも[initプロセス](https://docs.docker.com/reference/compose-file/services/#init)を使い、孤立した子プロセスをPostgreSQL本体に回収させない構成にしています。起動時の`npm ci`が完了してから`make check`を実行し、同じDBを使う通常の統合テストとrace検出は順番に実行してください。

環境変数はポートなど起動に必要なものへ絞ります。トークン・モデル・運用設定は可能な限り管理者専用画面で扱い、秘密値は暗号化保存する方針です。今回のHatchetローカルトークンは自動生成した専用volume、将来の管理画面が必要とするDB接続・復号鍵などは基盤設定として管理します。AI APIキーを`.env`やCIへ追加しないでください。

## DB・暗号鍵の復元訓練

```sh
make test-recovery
```

通常の開発環境を起動した後に実行します。専用profileの一時PostgreSQLへ合成データを作成し、[pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html)のcustom形式で退避、[pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html)で別の空DBへ復元します。鍵をDB dumpとは別ファイルへ退避し、元の鍵ファイルを除去してから読み戻します。既存のアプリDB・暗号鍵・volumeは使用せず、外部AI・メール・認証サービスも呼びません。

全テーブルの件数・内容hash、migration再適用、AI資格情報・接続資格情報・メール参照の復号、誤った鍵/鍵なしの拒否、無効化済みキーの非復活、管理者を含む所有者分離、通常実行ロールのDDL禁止を確認します。空DBと一行欠けたDBを検出する陽性対照も含みます。一時DBはポートや永続volumeを持たず、成否とも今回起動したコンテナだけを削除します。通常の`make up`では起動しません。

結果はGit対象外の`.local/recovery/run.XXXXXXXX/report.json`、合成dumpは`db/`、合成鍵は`keys/`、詳細ログは同じrunディレクトリへ保存します。ファイルは`0600`、runディレクトリは`0700`です。これらは合成訓練用であり、実データのバックアップではありません。実運用にはDBと鍵の別保管、オフホスト保管、Hatchet等の復旧、削除台帳の再適用、保持期限・RPO/RTOの検証が別途必要です。

## 本番向け構成

`compose.production.yaml`は開発用とは独立したAPI・Workerのみの構成です。Goは非rootユーザーで実行し、読み取り専用ファイルシステム・secretファイル・TLSを使用します。PostgreSQLとHatchet Liteを本番用定義から起動せず、専用DB・最小権限ロールとHatchet Cloudを接続先とします。

デプロイ時はmigration用接続ファイルを用意し、`docker compose -f compose.production.yaml run --rm migrate`をAPI・Worker更新より先に実行します。通常のAPIにDDL権限を与えません。APIには本番Clerkの公開設定を`.local/production/bootstrap.json`（`CYCRIO_BOOTSTRAP_FILE`で変更可）から読み取り専用secretとして渡します。暗号化鍵は`.local/production/keyring.json`を`/run/secrets/keyring`へ読み取り専用で渡します。ファイルはコンテナのUID/GID 10001が読み取れる所有者にし、鍵の権限は`0600`または`0400`にしてください。開発用の鍵を本番へコピーしないでください。

本番用の空DBにmigrationを適用した後、UID/GID 10001が書き込める専用の`.local/production/`を準備し、同じ本番接続先に対して初期鍵を生成できます。既存DBの場合は先に元の鍵を復元します。

```sh
docker compose -f compose.production.yaml run --rm --no-deps \
  -v "$PWD/.local/production:/keyring-output" \
  migrate manage init-keyring -keyring-file /keyring-output/keyring.json
```

作成した鍵は別保管先へバックアップしてからAPIを起動します。この操作は本番で自動再生成する仕組みではありません。

## 依存バージョン

導入・更新時に最新安定版を確認して固定します。現在はGo 1.27.3、Node 26.12.1、npm 12.2.1、PostgreSQL 18.6、Hatchet 0.114.0、Clerk Go 2.7.0 / JS 6.40.1 / UI 1.41.2です。TypeScriptは、最新版7にSvelteKit・svelte-checkが未対応のため、承認済みの6.0.3を使用します。

IMAPクライアントはユーザー承認済みの`go-imap v2.0.0-beta.8`に固定しています。安定版v1では初期接続中のエラーログを事前に制御できないため、初期化時からログ出力を設定できるv2をプレリリースの例外として採用しました。プロトコルのdebug出力は有効化しません。

PostgreSQL 16からこの構成へ更新する場合は、[開発DBの移行手順](deploy/local/upgrade-postgres.md)に従って既存データを退避・復元してから起動してください。18用volumeは16用とは別で、旧volumeのデータを自動移行するものではありません。

起動時の基盤接続情報は、サーバー上のsecretファイルを`CYCRIO_DATABASE_URL_FILE` / `CYCRIO_HATCHET_TOKEN_FILE`で指定します。既定の配置先は`.local/production/database_url` / `.local/production/hatchet_token`です。秘密値をイメージやGitに含めないでください。管理画面で設定可能な運用トークンの扱いは、その機能の実装時にDB暗号化保存へ統合します。

Webの本番成果物は`web/build/`です。`web/wrangler.jsonc`でCloudflare Workers Static AssetsのSPAフォールバックを設定しています。Cloudflareへの配信にはDocker内のWranglerを使用し、認証・権限・ドメインの設定は本番デプロイの工程で確認します。

```sh
docker compose run --rm --no-deps web npm run build
```

本番サービスとしての公開は、実メール処理・バックアップ・運用等の検証後に行います。
